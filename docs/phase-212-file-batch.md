# Phase 212：文件页的批量选择与批量操作

## 背景

服务端一直有 `POST /api/files/operations/batch`（1–20 项，逐项返回结果），但文件页没有多选模型，界面上只能一格格点「重命名 / 移动 / 删除」。上一阶段（Phase 211）把它列为「有意 API-only」，理由是「接它要先做选择态」。这一阶段把选择态补上了。

## 做了什么

**选择态**：目录列表每行前面加复选框，选择存在 `fileBatchSelection`（`path -> {name,type}`），上限 20 项与服务端一致。目录刷新或条目消失时按现有条目裁剪，避免拿着旧路径去改名。

**批量重命名**：统一前缀 + 三位序号，保留原扩展名。生成结果先在前端排重（同批内同名直接拒绝），最终仍以服务端逐项的 409 为准。

**批量移动**：填目标目录，把所选条目逐项 move 过去。

**结果呈现**：一行汇总（成功 / 失败 / 总数），失败项逐条显示「第 N 项（路径）：原因（服务端给的具体拒绝原因）」。

**不提供批量删除**：删除是破坏性操作，必须逐项确认。批量区连这个按钮都不放，测试里也锁死。

## 接口契约（沿用服务端既有语义）

```
POST /api/files/operations/batch
{ "operations": [ { "action": "rename", "path": "...", "name": "..." },
                  { "action": "move",   "path": "...", "destination": "..." } ] }

→ 200 { total, succeeded, failed, results: [ { index, ok, result } | { index, ok:false, statusCode, error, reason? } ] }
```

服务端会拒绝整批的情况：条数不在 1–20、包含 `delete` 而没带服务端删除能力（403）、写动作被执行策略关闭（403）。这三种都是整批拒绝，不是逐项跳过。

## 安全边界

- 批量操作全部走既有的 `file-manager.operateBatch` → `operate` 路径，根目录隔离、符号链接拒绝、不覆盖已存在目标等规则一条都没绕过。
- 批量删除刻意不开放；删除仍走「逐项确认 + 待确认的危险操作再确认」。
- 结果渲染只用 `textContent`，服务端返回的路径与原因不拼 HTML。
- 超过 20 项时前端直接拒绝并提示，不把超限批次发给服务端。

## 测试

新增 `tests/phase-212-file-batch.test.mjs`，8 例（Windows 上 6 通过 / 2 跳过）：

1. 批量重命名 + 批量移动后，文件确实落在预期位置（仅 Linux，依赖目录描述符）。
2. 单项失败不影响其余项：3 项里 1 成功 2 失败，且失败项都带 `error` 文案（仅 Linux）。
3. 非 Linux 上批次仍逐项拒绝，结构完整（`total` / `results` / 503）。
4. 超过 20 项 → 400；无能力的批量删除 → 403。
5–8. 前端：控件齐全、选择态与上限、走批量接口、结果渲染不拼 HTML、刷新时裁剪选择、批量区不出现删除。

## 遗留

- 批量重命名目前只有「统一前缀 + 序号」一种规则；文件页已有的 `rename-plan` / `rename-apply`（正则替换、预览）仍是单目录独立入口，后续可合并成同一套规则编辑器。
- 选择态不跨目录保留（换目录即清空），这是有意的：跨目录批量移动容易误伤。
